# Gameplay wire format

Gameplay messages use the shared protocol envelope and the session established by the handshake. Each direction continues its exact envelope sequence after the character lobby hands off the connection.

The version 18 command payload covers movement, facing, door use, item pickup, looting, targeted exploration skills, directly owned item-on-target use, same-map and cross-map elevator travel, ordinary cross-map exit grids, script-backed scenery stairs and ladders, agreed rest, inventory transfers, inventory-to-ground drops, shared modal state, bounded world-map route targets, and reserved combat attack messages. Every command carries its own command sequence, player and actor identities, expected session phase, and phase revision. Results report acceptance or a specific rejection and identify the authoritative event range. Inventory mutations name the source, item, moved quantity, and pre-move stack quantity. A bounded prototype/state descriptor lets the host assign identity when a player-held item has not appeared in the shared registry yet.

World-map route commands contain either a target within the 1400×1500 map or an explicit clear operation. The host accepts them only from the player whose approved proposal opened travel and publishes the resulting target. These events stage input only; world-map movement, time, encounters, and map loading remain disabled until the authoritative travel loop is connected.

When a loot move or direct player gift splits a stack, the host assigns a second entity ID to Fallout's newly copied remainder. The authoritative event carries the original item ID, remainder ID, counts, and host-verified descriptor. The receiving process performs the same split while binding the copy to the supplied ID. Whole-stack events use an invalid remainder ID. A player gift uses the acting actor as its source and the adjacent peer actor as its destination, so the same payload can carry ordinary items or caps without introducing a client-trusted trade result.

Gameplay wire version 29 adds direct trade commands and state events. A trade names two players and carries a monotonically increasing offer revision. Item lines contain shared item IDs and full-stack quantities; caps are offered separately. The host rejects stale revisions, invalid ownership, equipped items, insufficient caps, and a final confirmation when the players are no longer adjacent. Either participant can cancel. The commit event records the outcome, and an immediate authoritative checkpoint carries the actual item and cap ownership. Both offers are removed before either incoming stack is added, so stack merges cannot erase a still-pending offer.

A drop event additionally carries the host-selected ground tile and elevation. Ordinary multi-item requests are serialized as one-item commands because Fallout creates a separate ground object for each unit. Caps use a single quantity-bearing command and preserve their amount in the item descriptor. In both cases the guest waits for each accepted event before mutating inventory.

During live exploration, both host and guest input pass through the same command processor. The host validates ownership, phase revision, targets, and action feasibility, executes accepted commands, and publishes the authoritative event. Guest commands additionally receive an acceptance or rejection result. The host assigns one session-wide event sequence and appends every published event to the bounded recovery journal.

Door events include the host-selected frame, open state, and lock state. The guest applies those values directly and never invokes the door action or script. Pickup start events are presentation cues; after the deferred host animation and pickup script finish, a second ordered event carries success, final quantity, and mutable item state. The guest applies that concrete ownership change without invoking pickup logic. Attack events remain presentation boundaries backed by authoritative state snapshots, and live attack submission is blocked until combat phase and active-turn ownership are implemented.

Skill commands carry a registered target and one of First Aid, Doctor, Lockpick, Steal, Traps, Science, or Repair. The host validates and schedules Fallout's normal skill action under the acting player's build. The skill event is presentation-only: a replica never calls the skill action, target script, roll, or XP path. Authoritative snapshots supply the resulting actor, critter, door, non-door-scenery, item, global, map-variable, and timed-event state.

Item-use commands carry registered item and target identities. The host requires the item to be in the acting player's inventory and runs Fallout's normal action and target script. The peer event is only an ordered presentation boundary; consumption, scripts, queue changes, variables, reputation, and XP arrive through the authoritative checkpoint. Registered items absent from that checkpoint are destroyed on the replica.

Elevator commands carry an installed-data elevator type and destination level, not a client-selected object pointer. The host resolves both the source and destination through Fallout's elevator table and requires the acting player within four hexes of the source. For a same-map destination, the other player joins only when also within four hexes on that source elevation; otherwise the players remain on separate floors. A cross-map destination requires that proximity from both players, advances through the authoritative `Transition` phase, loads and registers the destination on each process, and rebinds the recreated remote actor under its existing identity. An accepted event carries the elevator type, destination map, each player's exact tile, elevation and rotation, and the final phase revision. The replica applies those values without opening the elevator UI or running its rule-bearing scripts.

Ordinary-exit commands name a canonically registered installed exit-grid entity. The host verifies its embedded destination, requires the acting player on the exact source hex and every connected participant within four hexes on the same elevation, then uses the same authoritative cross-map load boundary. The event carries the source identity, installed destination map, phase revision, and a bounded list of player ID, actor ID, tile, elevation, and rotation placements. Player and actor IDs must be unique and the acting actor must appear in the list. This roster-shaped event is the transition model for later rest and world-map work; it does not encode host/guest positions as fixed fields.

Scenery-transition commands name a registered stair or ladder object. The host requires the actor within four hexes, runs its use script once, redirects legacy protagonist movement and rotation to the acting player, and restores every non-acting player on same-map travel. The replica never runs that script. The result uses the same bounded player-keyed placement shape as ordinary exits. A captured cross-map request requires every participant nearby before loading the destination. The installed-data scenario proves independent same-map ladder travel; typed-stair paths are implemented but still need a dedicated fixture and convergence test.

Rest commands carry fixed minutes (10, 30, or one through six hours) or a distinct until-morning/noon/evening/midnight/healed choice; zero withdraws consent. The first accepted choice records a player-attributed proposal without changing the clock. A matching choice from every participant within 90 seconds authorizes the host to enter `Transition`, resolve time-of-day choices against its current clock, advance through due queue events and three-hour healing boundaries, and return to `Exploration`. Until-healed stops when all connected player actors reach maximum HP, including damage that occurs during rest. Wounded actors with no healing rate cannot propose it. A different choice replaces the proposal. The completed event carries the actual final time, phase revision, and an interruption flag for a queue interruption or safety bound; replicas apply the authoritative state without running rest, queue, or script rules. Proposal and completion events are journaled for reconnect replay. Until-healed has a 30-day ceiling and queue processing has a three-million-boundary safety ceiling.

Movement events include the exact sequence of hex directions chosen by the host, so the guest follows the authoritative route instead of independently pathfinding to the final tile. Facing is also a command because rotation affects later interaction presentation and must stay in the same event order.

Shared modal commands identify the modal kind and whether it is opening or closing. The host changes the session phase and publishes that phase plus its new revision in the ordered event. Dialogue and barter use `Dialogue`; rest, elevators, and world-map travel use `Transition`. While either phase is active, ordinary exploration commands fail phase validation. A recovery snapshot carries the authoritative phase and revision, so a peer that missed an open event still pauses and a snapshot in `Exploration` clears stale modal state.

All integer fields are fixed-width and big-endian. Decoders reject zero identities, sequences, and transfer quantities; unknown versions or message types; invalid phases; noncanonical booleans; nonzero reserved bytes; malformed lengths; trailing bytes; and inconsistent accepted or rejected results.

The headless test suite round-trips every message type and exercises malformed input. Installed-data two-process scenarios carry guest commands over TCP, apply host results and events on the guest, compare complete state digests, and replay the journal after authenticated reconnect.
